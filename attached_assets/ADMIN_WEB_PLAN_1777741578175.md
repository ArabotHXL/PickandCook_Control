## 1. 背景与问题

Pick & Cook 现在的运营动作（加菜谱、清数据、看分析、试 API）大多需要写脚本或者手敲 SQL：

- **加菜谱**：要去改 `data/recipes_packs/*.ts` 文件、或者跑 `scripts/upsert-recipes-from-excel.ts` 这类一次性脚本，再重启服务。
- **管理数据**：4.3 万产品、9 千多个菜谱、每天涨的用户和事件，没有可视化界面。前两天清生产库还是临时建了一个 `POST /api/admin/cleanup`，靠 curl 触发。
- **API 验证**：每加一个新接口都得手动 curl 或者去看日志。
- **分析数据**：`analytics_events / sessions / page_views` 已经在写了，但只有 SQL 才看得见。

随着 App 越长越大，这些"操作类"工作的时间成本会越来越高，而且容易出错。

## 2. 我们要建什么

一个**只给管理员用**的 Web 后台（暂定叫 *Pick & Cook Admin*），跑在和 mobile App 同一个 Express 后端之上。它只做一件事：**让运营 + 数据维护变成几次点击就能完成**。

四个核心模块：

| 模块 | 解决什么 | 关键功能 |
|---|---|---|
| 1. 菜谱管理 | 加新菜慢、改菜要改代码 | 列表 / 搜索 / 新建 / 编辑 / 删除 / 批量导入（CSV、Excel）/ 图片上传 / 实时预览 |
| 2. 数据管理 | 表里有什么、要不要清 | 用户 / 产品 / 菜谱 / Pantry 等关键表的浏览 + 过滤；一键触发已有的 `/api/admin/cleanup`；导出 CSV |
| 3. API 检测 | 接口有没有挂、回什么 | 把所有 admin/前台接口列出来，可以填参数发请求、看响应、保存常用请求 |
| 4. 分析看板 | 不写 SQL 看不到趋势 | DAU / WAU / MAU、留存、转化漏斗（注册 → 添加 Pantry → 完成做菜）、热门菜谱、扫码次数等 |

## 3. 替代方案对比

| 方案 | 现状 | 不够用的地方 |
|---|---|---|
| 直接登 Replit DB 跑 SQL | 现在就这么干 | 危险、不可重复、没人审计 |
| 用通用工具（Retool / Forest / Appsmith） | 拖拽建表，连 Postgres 即可 | 月费贵；不能直接调用我们已有的业务 API（比如菜谱评分、推荐引擎）；锁死在第三方平台 |
| 自建 Web 后台（本方案） | — | 需要前期投入 1–2 周搭骨架 |

**选自建的理由**：菜谱管理一定要走业务后端（要触发评分、过敏原检测、推荐重算），这是 Retool 这种通用工具最难做的部分，自建一次性投入小、长期维护成本低，还能复用现有的 React + TanStack Query 经验。

## 4. 验收指标

| 指标 | 现状 | 目标 |
|---|---|---|
| 加一个新菜谱所需时间 | 10 分钟 +（改 ts 文件、重启） | < 2 分钟（表单提交即生效） |
| 清生产数据所需操作 | 写脚本 / curl | 选目标 + 点确认 |
| 查看 DAU/留存所需操作 | 写 SQL | 打开看板 |
| 验证一个新 API | curl + 看日志 | 在 API 检测里填参数 → 一键发 |
| 后台自身可用率 | n/a | ≥ 99%（同 mobile App） |

## 5. 不做（Non-goals）

明确**不做**，避免无止境地扩张：

- **不取代 mobile App** — 用户端功能仍然在 Expo App 里。
- **不做权限层级** — 只有"管理员 / 非管理员"两档，不做团队 / 角色 / 工单审批。
- **不做内容工作流** — 没有"草稿 → 评审 → 发布"流程，编辑即生效（保留撤销）。
- **不做实时协作** — 假设同时只有一个管理员在用。
- **不做手机适配** — 桌面优先，手机能看但不优化。
- **不做对外 SaaS** — 永远只服务 Pick & Cook 一个项目。

## 6. 技术方案概览

- **位置**：作为一个新的 artifact 放在当前 Replit 项目里（`artifacts/admin-web/`），和 Expo App 共用一个 Replit 部署。
- **技术栈**：Vite + React + TypeScript + TanStack Query + shadcn/ui（成熟度高、和我们现有的 mockup-sandbox 同源）。
- **后端**：复用现有的 Express，所有新接口都挂在 `/api/admin/*`，强制 `role === 'admin'` 的中间件（已经有）。
- **认证**：复用 Expo App 的邮件登录 → JWT，管理员账号在 `users.role` 字段标记为 `admin`。
- **路由**：上线后用子路径 `/admin/*` 暴露，不开新域名。
- **图表**：Recharts（轻量、文档好）。
- **打包发布**：Vite build 产物由 Express 静态托管，跟 mobile Web 端走同一套部署流程。

## 10. 关键开放问题

下决定之前需要先想清楚：

1. **管理员账号怎么管？** 现在 `users.role='admin'` 是手动改 SQL。要不要做个"邀请管理员"的简单流程？
2. **后台域名 / 路径**：用 `/admin/*` 子路径就行，还是单开一个 `admin.pickncook.app` 子域名（更安全，但要配 DNS）？
3. **图片存储**：菜谱图片现在散落在 GCS / 本地 attached_assets。后台要不要顺便统一上传通道（推荐统一到 Object Storage 的 public/ 目录）？
4. **改菜谱的影响范围**：核心菜谱被改后要不要触发推荐缓存失效、评分重算？V1 先做"改完即生效，不重算"，但需要明确告知。
5. **审计粒度**：所有写操作都要写 `job_runs` 还是单独建一张 `admin_audit_log`？

## 11. 风险与缓解

| 风险 | 影响 | 缓解 |
|---|---|---|
| 后台权限被误用，删错生产数据 | 高 | 所有删除二次确认 + 默认 dryRun + 全部写审计 |
| 菜谱编辑直接改生产，没回滚 | 中 | V1 阶段加"最近 30 天编辑历史"，每次写操作存一份 diff |
| 自建后台维护成本随功能增加 | 中 | 严守 Non-goals，不做权限分级、不做工作流；每个 Phase 控制在 2 周内 |
| 后台和 mobile App 公用一个 Express，互相影响 | 中 | 后台路由全挂在 `/api/admin/*`，rate-limit 和日志独立 |
